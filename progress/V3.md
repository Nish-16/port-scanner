# V3 – Basic Service Detection (port-number based)

**Status:** Complete
**Environment:** Windows 11, Python 3.13.15, standard library only
**Previous version:** [V2](V2.md)

---

## 1. Goal

Go from

```
Port 22 → OPEN
```

to

```
Port 22 → OPEN → likely SSH
```

The main thing to learn is the difference between:

- **"A port is open"**: a fact. The TCP handshake succeeded.
- **"A service is probably running on that port"**: a guess, based on convention.

V3 makes that guess **only from the port number**. It never talks to the service.

Out of scope, not added: banner grabbing, protocol probing, vulnerability checks, UDP/SYN scanning, external packages, Nmap.

## 3. Code changes in detail

### 3.1 Service mapping (new)

```python
COMMON_SERVICES = {
    21: "FTP",   22: "SSH",   23: "Telnet", 25: "SMTP",  53: "DNS",
    80: "HTTP",  110: "POP3", 143: "IMAP",  443: "HTTPS",
    3306: "MySQL", 5432: "PostgreSQL", 6379: "Redis", 8080: "HTTP-Alt",
}
```

13 entries, kept small on purpose. **135 (Windows RPC) and 445 (SMB) are deliberately not included**, so on Windows they show `UNKNOWN` instead of being labeled from the port number alone.

### 3.2 `guess_service()` (new)

```python
def guess_service(port: int) -> str:
    return COMMON_SERVICES.get(port, "UNKNOWN")
```

`dict.get(key, default)` returns the default when the key is missing, so there's no `if` and no `KeyError`.

### 3.3 `scan_port()`: unchanged

It still returns `(port, is_open)` and still does only network work.

### 3.4 Result structure

| | V2 | V3 |
|---|---|---|
| Worker returns | `(port, is_open)` | `(port, is_open)` (same) |
| `scan_ports()` returns | `list[int]` | `list[tuple[int, str]]` → `[(port, likely_service), ...]` |

```python
port, is_open = future.result()
if is_open:
    open_ports.append((port, guess_service(port)))
```

**Why not `(port, is_open, service)` from the worker, as first suggested?**
- The service guess isn't network work. It's a dictionary lookup, so it doesn't need to run in a worker thread.
- Keeping `scan_port()` unchanged means the TCP logic from V1/V2 stays exactly as it was.
- Closed ports never get a service value, because none is needed.
- The lookup happens only **after** a port is known to be open, and it makes **no second connection**.

**Sorting** still works with `open_ports.sort()`, because Python compares tuples by their first item (the port number) first.

### 3.5 Output

```
PORT     STATE      LIKELY SERVICE
----------------------------------------
135      OPEN       UNKNOWN
8080     OPEN       HTTP-Alt
```

- The column header says **LIKELY SERVICE**, not SERVICE, so the output itself says it's a guess.
- Columns are aligned with f-string padding: `f"{port:<9}{'OPEN':<11}{service}"`.
- The title is now centered: `"TCP PORT SCANNER V3".center(40)`.

### 3.6 No `--services` flag (decision)

Service info is always shown for open ports. A flag to turn off one extra column would add a code path and a CLI option without any real benefit. The simpler interface wins.

## 4. V3 flow

```
User
  ↓
CLI arguments (argparse) → validate
  ↓
Resolve hostname (gethostbyname)
  ↓
Thread pool (ThreadPoolExecutor)
  ↓
TCP connect scan (scan_port, unchanged)  ← only network step
  ↓
Is port OPEN?
  ↓ YES
Look up common service (dictionary, by port NUMBER; no network)
  ↓
(port, likely_service)
  ↓
Sort results
  ↓
Display table + summary
```

## 6. Why service detection isn't guaranteed

- Port numbers are **conventions**, not rules. The OS will let any program listen on any free port.
- SSH is often moved to 2222. Development web servers use 3000, 5000, 8000 and 8080. Anything can run on 80.
- V3 never sends or reads a single byte from the service, so it has no evidence beyond the number.
- Shown in practice: a silent test socket on 8080 was labeled `HTTP-Alt`.

The correct wording is **"port 80 is commonly associated with HTTP"**, never "port 80 is HTTP".

## 7. Known limitations of V3

- Service = guess from the port number only, and it can be wrong
- Only 13 known ports; everything else is `UNKNOWN`
- No banner grabbing or protocol probing
- TCP only, IPv4 only, can't tell closed from filtered
- Output appears only after the whole scan finishes

## 8. Concepts learned

1. **Port vs service**: a port is a numbered endpoint; a service is the program/protocol listening on it
2. **Well-known ports**: standards (IANA assignments) and habit make port 80 the usual home of HTTP
3. **Convention, not guarantee**: any program can bind any free port
4. **Service detection**: working out *what* is behind an open port
5. **Inference vs identification**: V3 infers from the number; real identification needs evidence from the service itself
6. **No extra connection**: V3 stays a pure connect scan; asking the service is a separate, more intrusive step
7. **Banner grabbing (next)**: read what the service sends after connecting (e.g. `SSH-2.0-OpenSSH_9.6`), which is evidence from the service rather than a guess
8. **`dict.get(key, default)`**: a simple, safe lookup with a fallback
9. **Tuple sorting**: tuples compare item by item, so `(port, service)` sorts by port
