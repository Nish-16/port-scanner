# V1 – Sequential TCP Connect Scanner

**Status:** Complete
**Environment:** Windows 11, Python 3.13.15, standard library only

---

## 1. Goal

Build the simplest possible working port scanner, in order to learn:

- IP addresses and hostnames
- TCP and ports
- sockets and connection attempts
- timeouts
- open vs closed ports
- sequential scanning
- command-line arguments

Speed was deliberately **not** a goal. V1 scans one port at a time.

## 3. Command-line interface

```
python scanner.py <target> [--start N] [--end N] [--timeout SECONDS]
```

| Argument | Type | Default | Meaning |
|---|---|---|---|
| `target` | str (positional) | – | Hostname or IPv4 address |
| `--start` | int | 1 | First port |
| `--end` | int | 1024 | Last port (inclusive) |
| `--timeout` | float | 1.0 | Seconds to wait per connection |

Built with `argparse`, which also rejects non-numbers like `--start abc` by itself.

---

## 4. Program structure

```
main()
 ├── parse_arguments()          read CLI arguments
 ├── validate_arguments()       check ports / timeout, return error text or ""
 ├── resolve_target()           hostname → IPv4 via socket.gethostbyname
 ├── print_header()
 ├── start timer                time.perf_counter()
 ├── scan_ports()               loop over every port, one by one
 │     └── scan_port()          one TCP connection attempt
 ├── stop timer
 └── print_summary()
```

### Functions

| Function | Returns | Job |
|---|---|---|
| `parse_arguments()` | `argparse.Namespace` | Defines and reads CLI options |
| `validate_arguments(start, end, timeout)` | `str` | Error message, or `""` if valid |
| `resolve_target(target)` | `str` | IPv4 address; raises `socket.gaierror` on failure |
| `scan_port(ip, port, timeout)` | `bool` | `True` if the port is open |
| `scan_ports(ip, start, end, timeout)` | `list[int]` | All open ports, printed as found |
| `print_header(...)` / `print_summary(...)` | `None` | Output formatting |
| `main()` | `None` | Ties everything together, handles errors |

### The core function

```python
def scan_port(target_ip: str, port: int, timeout: float) -> bool:
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
        sock.settimeout(timeout)
        result = sock.connect_ex((target_ip, port))
    return result == 0
```

- `AF_INET` → IPv4
- `SOCK_STREAM` → TCP
- `settimeout` → give up after N seconds
- `connect_ex` → returns an error code (0 = success) instead of raising an exception
- `with` → the socket is always closed, even if an error happens

### The sequential loop

```python
for port in range(start_port, end_port + 1):
    if scan_port(target_ip, port, timeout):
        print(f"[OPEN] Port {port}")
        open_ports.append(port)
```

`end_port + 1` is needed because `range()` leaves out its end value, and the port range includes both ends.

## 5. Design decisions

| Decision | Why |
|---|---|
| `connect_ex` instead of `connect` | Closed ports return an error code instead of raising, so there are no try/except blocks or error messages for every closed port |
| `with socket.socket(...)` | The socket is closed automatically, so it can't be forgotten |
| `validate_arguments` returns a string | Keeps `main()` flat and readable, with one place for all validation rules |
| Errors go to `stderr`, exit code `1` | The usual command-line convention for "something went wrong" |
| `KeyboardInterrupt` caught around the scan | Ctrl+C prints a friendly message instead of a traceback |
| `OSError` caught around the scan | Only real scanner-level failures (e.g. out of sockets) show an error; closed ports never reach this handler |
| Constants at the top (`DEFAULT_TIMEOUT`, `MAX_PORT`…) | No unexplained numbers in the code |
| No classes, threads or extra libraries | Every line should be explainable in an interview |

## 6. Validation rules

| Input | Error shown |
|---|---|
| start port outside 1–65535 | `Error: start port must be between 1 and 65535.` |
| end port outside 1–65535 | `Error: end port must be between 1 and 65535.` |
| start > end | `Error: start port cannot be greater than end port.` |
| timeout ≤ 0 | `Error: timeout must be greater than 0.` |
| unknown hostname | `Error: could not resolve hostname '<name>'.` |
| non-integer port | argparse usage message (exit code 2) |

## 8. Discovery: Windows timing behaviour

Each closed port on localhost took about **1 second** (the full timeout) instead of failing instantly.

**Reason:** on Linux, a closed port answers with a TCP RST and the connection is refused immediately. On Windows, the OS keeps retrying the connection for about 2 seconds before giving up, even on localhost. With a 1 s timeout, the timeout almost always runs out first.

**Consequence:**

```
scan time ≈ number of ports × timeout
1024 ports × 1 s ≈ 17 minutes
```

This is exactly the problem V2 solves.

---

## 9. Known limitations of V1

- Sequential: very slow for large ranges
- TCP only, IPv4 only
- Can't tell "closed" apart from "filtered"
- No service detection, banner grabbing or vulnerability checks
- Connect scan: completes the full handshake, so the target can log it

## 10. Concepts learned

1. **Socket**: one end of a network connection that the OS provides to the program
2. **`AF_INET`**: IPv4 addressing
3. **`SOCK_STREAM`**: TCP, a reliable connection-based byte stream
4. **Why TCP**: the three-way handshake (SYN → SYN-ACK → ACK) is itself the test for "is something listening?"
5. **`connect_ex()`**: attempts the handshake and returns an error code instead of raising
6. **Return value 0**: OS calls use 0 for "success, no error", so 0 means the handshake completed
7. **Timeout**: the longest time we wait; protects against firewalls that silently drop packets
8. **Closing sockets**: every socket uses an OS handle, and leaking them eventually crashes the program
9. **1–1024 = 1024 ports**: inclusive range, `end − start + 1`
10. **Why sequential is slow**: time is spent waiting on the network, not computing, and the waits add up one after another
