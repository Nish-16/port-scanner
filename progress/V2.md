# V2 – Multithreaded TCP Connect Scanner

**Status:** Complete
**Environment:** Windows 11, Python 3.13.15, standard library only
**Previous version:** [V1](V1.md)

---

## 1. Goal

Make the scanner much faster by scanning many independent ports **at the same time**, using `concurrent.futures.ThreadPoolExecutor`.

V2 is still the **same TCP connect scanner**. What changed is **how the work is scheduled**, not how a single port is checked.

```
V1:  port 1 → wait → port 2 → wait → port 3 → wait ...

V2:  Thread 1 → port 1 → waiting ─┐
     Thread 2 → port 2 → waiting ─┤  waits overlap
     Thread 3 → port 3 → waiting ─┤
     Thread 4 → port 4 → waiting ─┘
```

Out of scope, not added: UDP, SYN/stealth scans, raw sockets, service detection, banner grabbing, asyncio, multiprocessing.

## 3. Code changes in detail

### 3.1 New import and constants

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

DEFAULT_THREADS = 100
MIN_THREADS = 1
MAX_THREADS = 1000
```

### 3.2 New CLI argument

```
--threads N     number of worker threads, 1-1000 (default: 100)
```

### 3.3 Validation

`validate_arguments()` gained a `threads` parameter and one new rule:

```python
if threads < MIN_THREADS or threads > MAX_THREADS:
    return f"threads must be between {MIN_THREADS} and {MAX_THREADS}."
```

**Why the maximum is 1000:** each thread uses memory, and each running scan holds an open socket. Thousands of threads would waste resources and could hit OS limits. For a scanner that mostly waits on the network, 1000 concurrent attempts is already far more than a learning project needs.

### 3.4 `scan_port()`: return value only

The socket logic is **the same as V1**. Only the return value changed:

| | V1 | V2 |
|---|---|---|
| Signature | `-> bool` | `-> tuple[int, bool]` |
| Returns | `result == 0` | `(port, is_open)` |

**Why:** in V1 the loop always knew which port it had just scanned. In V2 results come back in *finishing* order, so each result has to carry its own port number.

### 3.5 `scan_ports()`: the main change

**V1:**
```python
for port in range(start_port, end_port + 1):
    if scan_port(target_ip, port, timeout):
        print(f"[OPEN] Port {port}")
        open_ports.append(port)
```

**V2:**
```python
open_ports = []
executor = ThreadPoolExecutor(max_workers=threads)
try:
    futures = []
    for port in range(start_port, end_port + 1):
        future = executor.submit(scan_port, target_ip, port, timeout)
        futures.append(future)

    for future in as_completed(futures):
        port, is_open = future.result()
        if is_open:
            open_ports.append(port)
finally:
    executor.shutdown(wait=True, cancel_futures=True)

open_ports.sort()
return open_ports
```

Step by step:

1. **Create the pool**: up to `threads` workers.
2. **Submit** one `scan_port` task per port. `submit()` returns immediately with a **Future**, a placeholder for a result that doesn't exist yet.
3. **`as_completed()`** hands back each Future as soon as its task finishes.
4. **Main thread** reads `(port, is_open)` and records the open ones.
5. **Shutdown** (in `finally`, so it always runs).
6. **Sort** the open ports.

### 3.6 Why `try/finally` instead of `with ThreadPoolExecutor(...)`

A `with` block calls `shutdown(wait=True)` when it ends, which waits for **every queued task**. After a Ctrl+C in the middle of a large scan, that could mean waiting minutes for thousands of ports nobody wants any more.

`shutdown(wait=True, cancel_futures=True)`:
- **cancels** tasks that haven't started yet
- **waits** only for tasks already running (at most one `--timeout`), so their sockets close properly

### 3.7 Output changes

- Header now says `TCP PORT SCANNER V2` and shows `Threads: N`.
- `[OPEN]` lines are printed **after** the scan, sorted, instead of as each one is found. With threads, printing as found would give a scrambled order.

## 4. Thread safety design

```
worker thread → scans one port → returns (port, is_open)
                                        ↓
main thread   → reads result   → appends to open_ports (only it touches the list)
```

- Workers **never** modify shared data.
- Only one thread (main) writes to `open_ports`, so no lock is needed.
- This is simpler and less error-prone than having 100 threads append to a global list.

## 5. Test results (real runs)

### 5.1 Benchmark: ports 1–100 on `127.0.0.1`, `--timeout 1`

| Threads | Time taken | Speedup vs 1 thread |
|---:|---:|---:|
| 1 | 100.67 s | 1× |
| 10 | 10.08 s | ~10× |
| 100 | 1.03 s | ~98× |

### 5.2 Full default range

| Version | Ports | Threads | Time | Open ports |
|---|---|---|---|---|
| V1 (estimated from 1–100 run) | 1–1024 | – | ~17 min | – |
| V2 | 1–1024 | 100 | **11.10 s** | 135, 445 |

### 5.3 Why the speedup looks perfectly proportional

On Windows, nearly every closed port waits the full timeout (see [V1 §8](V1.md#8-discovery-windows-timing-behaviour)), so every task takes the same ~1 s. So 100 ports ÷ 100 threads ≈ 1 round of 1 s.

**This won't always hold.** Real performance depends on:
- network behaviour and latency
- operating system (Linux refuses closed ports almost instantly, leaving less waiting to overlap)
- the timeout value
- how the target responds
- firewalls that drop packets
- thread count
- system resource limits

### 5.5 Sorting verification

Real listeners were opened on ports 50007, 50002, 50009 and 50004, and random delays were injected into the workers:

```
finish order : [50002, 50007, 50009, 50004]
returned     : [50002, 50004, 50007, 50009]
sorted OK    : True
```

The finishing order was scrambled, but the output was still sorted.

### 5.6 Socket and thread cleanup after Ctrl+C

Measured by counting live threads and the process's TCP sockets (via `netstat`):

| Moment | Threads alive | Open TCP sockets |
|---|---:|---:|
| During scan | 102 (main + 100 workers + test timer) | 88 |
| After Ctrl+C | 1 | 0 |

Nothing was left running.

### 5.7 Note on how Ctrl+C was tested

The first attempts to send a real Ctrl+C did nothing. The reason was the test environment, not the scanner:

1. The tool's shell has **no console attached**, so console Ctrl+C events had nowhere to go.
2. Inside a new console, processes still inherited a **"Ctrl+C disabled"** flag from the tool environment. Even a plain `time.sleep(20)` ignored it.
3. Fix: a small wrapper re-enabled Ctrl+C (`SetConsoleCtrlHandler(NULL, FALSE)`) and then ran the **unmodified** `scanner.py` via `runpy`.

With that setup, the real scanner reacted correctly and exited **1.15 s** after Ctrl+C. The delay is expected: the scans already in progress finish within the 1 s timeout and close their sockets.

In a normal terminal none of this is needed. Just press Ctrl+C.

## 7. Known limitations of V2

- TCP only, IPv4 only
- Can't tell "closed" apart from "filtered"
- Open ports only appear once the whole scan finishes
- After Ctrl+C, the program waits up to one `--timeout` for running scans to finish
- No service detection, banner grabbing or vulnerability checks

## 8. Concepts learned

1. **Thread**: a separate path of execution inside the same program, sharing the same memory
2. **Why threads help here**: while one thread waits for a network reply, others can start their own connection attempts
3. **I/O-bound vs CPU-bound**: the scanner spends its time waiting, not computing. Threads help I/O-bound work. For CPU-heavy work in Python they help little, because of the GIL (the rule that lets only one thread run Python code at a time).
4. **ThreadPoolExecutor**: a reusable pool of worker threads that takes tasks from a queue
5. **`max_workers`**: the *maximum* number of tasks running at once, not a guarantee that that many are always active
6. **Future**: a placeholder returned by `submit()`; `.result()` gives the value once the task is done
7. **Returning results vs shared state**: workers return values and only one thread collects them, so there are no race conditions and no locks
8. **Completion order ≠ submission order**: threads finish whenever their network reply arrives
9. **Sorting**: makes output deterministic and independent of thread timing
10. **Why a thread cap**: each thread uses memory and a socket, and unlimited threads could exhaust system resources
11. **Graceful shutdown**: queued tasks can be cancelled, but running threads can't be killed from outside and have to finish on their own (bounded by the timeout)
